# UX qcheck — 操作フロー・文言の品質チェック

pytest では検証できない「操作の流れ」「文言の妥当性」を対象にした、再実行可能な手順書。
各項目は VISION.md の `[qcheck]` 設計思想に対応する。

判定記号: ✅ PASS(合格) / ⚠️ FAIL→修正済み / 🔲 未実施(要人手・要実トークン)

安全上の注意: 以下の手順はすべて **実際のトークンを使わず、confirm() をキャンセルする**
ことで、GitHub への実際の書き込み(取得の実行・ストックの削除)を発生させずに検証している。
ブラウザの `window.fetch` / `window.confirm` / `window.alert` を一時的に差し替えるだけの、
クライアント側だけで完結する安全な検証方法。

## QC-UX-01: 新規取得の確認ダイアログ

**対応する設計思想**: 機能別ルール(背景透過)「新規取得ではAPI消費見込みを事前提示し、
確認を取る」`[qcheck]`(文言・UXの妥当性)

**手順**(GUI/Web版):
1. 「ロゴを取得する」の入力欄に、ストックに無い企業名を1件入力する
2. 「ロゴを取得」を押す(`confirm()` をキャンセルして実際には進めない)
3. 表示された確認文言を記録する

**手順**(CLI版):
1. `python src/main.py`(APIキー設定済み・企業リスト用意済みの状態)を実行し、
   確認プロンプトの文言を確認、`n` で中断する
2. `--force` 付きでも実行し、追加の警告行が出るか確認する

**期待結果**: 件数とAPI消費の見込みが明示され、内容が理解できる文言になっている

**実施結果**: ✅ PASS(2026-08-25)

Web版(新規企業名):
> `1社を処理します。よろしいですか?`

CLI版(`confirm(1, force=False)`、標準出力を捕捉):
```
これから 1 件を処理します。
  ※ 背景削除は1件につき remove.bg のクレジットを1消費します(取得画像がすでに透過の場合とキャッシュがある場合を除く)。
続行しますか? [y/N]:
```
CLI版(`force=True`)では追加行を確認:
```
  --force が指定されているため、キャッシュを使わず全件でAPIを呼びます。
```
`y`/`yes` いずれの入力でも承諾として扱われることをコードレベルで確認済み。

**実施結果**: ✅ PASS(2026-08-25)

「、」区切りで列挙される仕様(コード確認)。

## QC-UX-08: コピー機能(成功時の視覚フィードバック / 失敗時のフォールバック案内)

**対応する設計思想**: なし(コア機能のUX確認)

**手順**: カードの「コピー」ボタンの `copyPng()` ロジックを直接実行し、
(a) クリップボード書き込み成功時にボタン文言が「コピーしました」に変わり1.5秒後に戻ること、
(b) 書き込み権限が無い場合に代替手段を案内するアラートが出ることを確認する

**期待結果**: 成功時は一時的な文言変化、失敗時は「右クリック→画像をコピー」という
具体的な代替操作が示される

**実施結果**: 🔲 (a)は環境制約により未実施 / ✅ (b) PASS(2026-08-25)

このブラウザ自動操作環境では `navigator.clipboard.read/write` が
`NotAllowedError` (権限拒否)となり、実際のOSクリップボードへの書き込み成功は
自動検証できなかった(サンドボックスの制約。ドキュメントのフォーカス取得は
`document.hasFocus() === true` まで確認したが、権限自体が拒否される)。
**(b) 失敗時フォールバックの経路は直接実行で確認**:
> `コピーに失敗しました。画像を右クリック→「画像をコピー」をお試しください。`
(a) の成功パスは、2026-08-25 の実機検証(`tools/verify_copy_combo.py`、実際の
PowerPoint に Ctrl+V で透過画像が貼り付けられることを確認済み)で担保されている。
定期的な人手での再確認を推奨(ブラウザ更新等でクリップボードAPIの挙動が
変わり得るため)。

## QC-UX-09: 実行の取り違え防止(run_idベースの追跡)

**対応する設計思想**: 機能別ルール(GitHub版)「ビューワーは『自分が依頼した実行』を
run_id で確定してから見守る。時刻の前後関係やクライアント時計には依存しない」`[qcheck]`

これは過去に確定した重大バグ(他人・過去の実行を自分の結果と誤認する)の再発防止確認。

**手順**: `window.fetch` をモックし、以下のシナリオを `findNewRunId` / `waitForRunById` /
`waitForPages` に直接与えて検証する。
1. 依頼前に既存run(1,2,3。3は直近failure)がある状態で自分が依頼 → 新規run(4)だけが
   自分の実行として特定されるか
2. `last_run.json` が「他人の実行結果(run_id=999)」→「自分の結果(run_id=4)」の順で
   反映される状況で、他人の結果を早合点して完了と見なさないか

**期待結果**: いずれのシナリオでも、既存の古い実行・他人の実行結果を自分のものと
誤認しない

**実施結果**: ✅ PASS(2026-08-25)

シナリオ1:
```
before=[1,2,3] → findNewRunId → runId=4(3を誤って選ばない)→ waitForRunById(4).conclusion="success"
```
シナリオ2:
```
1回目のlast_run.json(run_id=999)を無視し、2回目(run_id=4)で完了と判定(tookCalls=2)
```
両方とも設計通りに動作。この設計思想はJSロジックのため pytest 対象外(`[qcheck]`のまま維持)。

## QC-UX-10: 多重実行の防止

**対応する設計思想**: なし(追加観点。実行中の二重操作によるレース事故の防止)

**手順**: `fetchBusy` フラグが立っている間に別の取得操作を試みたときの挙動をコードで確認する

**期待結果**: 「実行中です。完了までお待ちください。」等の案内が出て、二重に依頼されない

**実施結果**: ✅ PASS(2026-08-25、コードレビューによる確認)
`runFetch()` 冒頭の `if (fetchBusy) { setFetchStatus("実行中です。完了までお待ちください。", "working"); return; }`
により、実行完了(`finally` で `fetchBusy = false`)まで新たな依頼を受け付けない。
